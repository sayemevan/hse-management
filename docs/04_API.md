## Conventions

- Base path `/api/v1`; resources are kebab-case plural nouns.
- Methods: GET read · POST create · PATCH update · DELETE archive/soft delete.
- Every response uses one envelope (`packages/shared/src/api/response.ts`):

```jsonc
// success
{ "success": true,  "message": "OK", "data": { }, "meta": { "page": 1, "pageSize": 20, "total": 0 } }
// error
{ "success": false, "message": "Human-readable message", "error": { "code": "VALIDATION_FAILED", "requestId": "…", "details": [ ], "params": { } } }
```

- Clients translate errors by `error.code` (with `error.params` for values such as minutes); `message` is an English fallback (PLT-03). Codes: `packages/shared/src/api/error-codes.ts`.
- Every request carries an `x-request-id` (generated when absent), returned in the response headers and in error bodies.
- **Same origin (T-4):** the API is served on the same host as the web app under `/api/*` (a Workers route in deployed environments, the Next.js dev proxy locally). The tenant is resolved from the host (PLT-02).
- Authentication: `Authorization: Bearer <access JWT>` (15 minutes) plus an `HttpOnly; SameSite=Strict` refresh cookie scoped to `/api/v1/auth`. Every authenticated request also checks the session in the database (T-2).
- Cookie-based endpoints (`/auth/refresh`, `/auth/logout`) require an `Origin` header matching the host.

**Read-only mode (PLT-11, T-24).** On a company subdomain, every `POST`, `PUT`, `PATCH` and `DELETE` answers **403 `SUBSCRIPTION_READ_ONLY`** (`params.readOnlySince`) while the subscription is read-only, except the allow-list in `modules/billing/read-only.middleware.ts`: `/auth/*`, `/invitations/accept` and `/subscription/*`. A unit test lists every company write route, so a new one is blocked unless it is reviewed onto the list.

**Plan limits (PLT-12).** Invitations and uploads may answer **409 `PLAN_LIMIT_REACHED`** with `params: { resource: 'users' | 'projects' | 'storage', limit, used, free }`. It replaces `PLAN_USER_LIMIT_REACHED`, which is no longer sent.

**Idempotent writes (PLT-29, T-69).** Offline-capable write routes accept `Idempotency-Key` (UUID; optional online, always sent by the sync engine). A repeat with the same body and user replays the first answer (same status, the resource read again, header `Idempotent-Replayed: true`) without running the change again; the same key with another body or user → `IDEMPOTENCY_KEY_REUSED` (422); a key that is not a UUID → `IDEMPOTENCY_KEY_INVALID` (400). A create with a device-made id used by another record → `RECORD_ID_TAKEN` (409). The sync engine also sends `X-Captured-At` (the capture time; more than a day ahead is replaced by the receive time, O-129) and `X-Device-Id`; both go into the audit entry with the key (O-130).

**Conflicts (T-70).** An offline update whose `baseVersion` is not the record's version changes nothing and answers `SYNC_CONFLICT` (409) with `params: { conflictId, serverVersion }`; both versions are in `sync_conflict` and the user is notified (`sync.conflict`, reminded once after 2 days, O-131). Online, the same mismatch answers `SYNC_CONFLICT` without a `conflictId` (reload and edit again).

Read-only mode: the conflict resolution and the three probe writes are blocked (reviewed in `test/lifecycle.test.ts`). Daily job `sync.maintenance`: expired idempotency keys and conflict reminders.
