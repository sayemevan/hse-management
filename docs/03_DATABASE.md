## Physical conventions (D1 / SQLite)

| Concept          | Storage                                                                  |
| ---------------- | ------------------------------------------------------------------------ |
| Primary key `id` | `TEXT` UUID v4, generated in the application                             |
| Timestamps       | `INTEGER` epoch milliseconds, UTC                                        |
| Audit columns    | `created_at`, `created_by`, `updated_at`, `updated_by` on every table    |
| Soft delete      | `deleted_at`, `deleted_by` where the business rules require archiving    |
| Tenant columns   | `company_id` on every business table; `project_id` on operational tables |
| JSON             | `TEXT`, parsed and validated with Zod in the repository                  |

These are implemented as reusable helpers in `apps/api/src/database/columns.ts`.

## Working with the schema

- Tables are defined in `*.schema.ts` files inside their module (`apps/api/src/modules/<module>/`, `apps/api/src/platform/<service>/`). Only that module's repository reads or writes them.
- `npm run db:generate --workspace @hse/api` creates a SQL migration in `apps/api/migrations/`; hand-written SQL (triggers) goes in a custom migration (`drizzle-kit generate --custom`).
- `npm run db:migrate:local --workspace @hse/api` applies migrations to the local D1. Integration tests apply them to an in-memory D1 on every run.
- Atomic multi-table writes use `UnitOfWork` (one D1 batch). `db.transaction()` is not supported by D1 (ADR-001).
