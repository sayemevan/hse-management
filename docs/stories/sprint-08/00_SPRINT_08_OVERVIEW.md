## Goal

Every problem found on site ends with an **owner, a deadline and a verified fix** (Doc 13 §2). This sprint builds the **one action engine** of the platform (Doc 13 §18): actions are created by hand now, and by inspections, safety events, permits and audits from Sprint 10 onwards through the same contract, without the engine knowing those modules (Doc 13 §3, review §4 recommendation 1). An action moves **Open → In Progress → Completed → Verified → Closed** (D-12); the owner records progress and completion evidence, an authorised person who isn't the owner verifies it, and only verified actions close (Doc 13 §10, §16). People discuss an action in a **comment thread**, the reusable comment service of Doc 04 §11 that was moved here from Sprint 6 (O-57). Owners are reminded before and after the due date, and overdue actions stay visible until they are resolved (Doc 13 §9, §13).

## Technical decisions (approved, D-52)

| ID   | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | Why                                                                                                                                                                                                                                |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| T-57 | A new **`action` module** with **one `action` table** for every source. An action stores `source_module`, `source_record_id` and a **`source_label` snapshot** (for example "Inspection INS-0042, item 7"). Modules that create actions register an **`ActionSource`** with the engine (`registerActionSource({ module, describe(companyId, recordId) → { label, href, projectId }, canView(principal, recordId) })`) and create actions through the module's contract **`ActionEngine.create(uow, input)`**, in their own `UnitOfWork`. The engine never imports a source module. Sprint 8 registers `manual` (no record) and `action` (follow-up of a closed action, O-97). | Doc 13 §3 "The Action Engine should never depend on one specific module"; settles C-13: the engine is built before its consumers and they plug in later. A failed inspection submission never leaves a half-created action behind. |
| T-58 | The **workflow is data**: one transition table in the shared package, `ACTION_WORKFLOW`, lists each allowed move (`from`, `to`, who may make it — `owner`, `collaborator`, `verifier`, `closer`, `manager` — and the fields it requires). The API checks every status change against it and the web app reads it to show only the buttons that apply. It is the first use of the **shared workflow-definition format** of review §4 recommendation 4; Inspection, Safety Event and Permit reuse the format.                                                                                                                                                                   | One definition for API and UI; no transition rules spread across services; Doc 03 rule 16 (workflows not hard-coded in screens).                                                                                                   |
| T-59 | **Due state is computed, not stored** (as T-50): one shared function `actionDueState(dueOn, status, today)` → `done` (Completed, Verified or Closed), `on_track`, `due_soon` (within 3 days), `due_today`, `overdue`, where `today` is the calendar date in the company's time zone. `due_on` is a date column, indexed with `status`; list filters turn due states into date ranges.                                                                                                                                                                                                                                                                                         | A stored "overdue" flag would go stale every midnight; the same pattern as workforce expiry.                                                                                                                                       |
| T-60 | **Record numbers** come from a new shared **`record_counter`** table (`project_id`, `kind`, `next_value`) owned by the `project` module and exposed as `RecordNumbers.next(uow, projectId, kind)`: one conditional `UPDATE … RETURNING` inside the change's batch, so two actions created at the same moment never share a number and a failed change leaves no gap. Actions use kind `action` and show as **`{project code}-ACT-0001`** (O-98). Inspections, permits and events will add their own kinds.                                                                                                                                                                    | Numbers per project, without a race, reusable by every later module (Q-23). D1 runs a batch as one transaction.                                                                                                                    |
| T-61 | The **owner** is a column on `action` (indexed, for "My actions") and every owner change is a row in **`action_owner_history`** (from, to, by, reason, at). **Collaborators** are rows in `action_collaborator` (added and removed, never deleted: `removed_at`). Owners and collaborators must be **users** who can view the project (O-101).                                                                                                                                                                                                                                                                                                                                | Doc 13 §8 "Ownership history must remain available"; indexed queries for the owner's lists.                                                                                                                                        |
| T-62 | Progress, completion, verification, rejection, closure and void notes are rows in one immutable **`action_update`** table (`kind`, `note`, `percent`, `method`, `by`, `at`), protected by triggers against UPDATE and DELETE like `audit_log`. Files are linked through **`action_file`** (`file_id`, `update_id` or none, `kind` = `evidence` or `attachment`). A new file category **`action_evidence`** is **module-served** (T-49): only the action routes serve it, after checking the reader can view the action.                                                                                                                                                       | Doc 13 §11 "Evidence remains permanently linked to the action"; §16 never deleted. Evidence photos may show people and must not be readable through the generic file route.                                                        |
| T-63 | A new **`comment` platform service** with one `comment` table for every module (`entity_type`, `entity_id`, `project_id`, `author_id`, `body`, `created_at`, `edited_at`). A module turns comments on for a record type by registering a **`CommentTarget`** (`canView`, `canComment`, `isLocked`, `participants` to notify) and **mounts the routes under its own record** (`/projects/{projectId}/actions/{actionId}/comments`), so the module's permission checks and the project-in-URL rule (T-45) still apply. Edits keep the old text in the audit log.                                                                                                                | Doc 04 §11: "Any module should be able to receive comments without creating separate comment systems." Access stays with the module that owns the record.                                                                          |
| T-64 | A new daily job **`actions.due`** (company time zone): for each owner, **one digest notification per day** when they have actions due today or overdue ("2 actions due today, 3 overdue"); **one notification per action** the day before the due date and on the first overdue day; on the first overdue day of a **High** or **Critical** action the person who assigned it is told too. **Critical** overdue actions are listed in the owner's digest **every day** until completed (Doc 13 §13 "recurring reminders until resolved"). Every send uses a `ReminderService` key, so a repeated or missed run is safe.                                                       | Same shape as the workforce digest (T-51); one digest keeps the bell useful for people with many actions.                                                                                                                          |
| T-65 | **Who sees an action:** holders of `projects.actions.view` on the project see all its actions; anyone with `projects.view` on the project also sees the actions they **own, collaborate on or created** ("participants"). A source module may narrow this further for its own actions through `ActionSource.canView`. Comments, files and history follow the action's access.                                                                                                                                                                                                                                                                                                 | Workers and foremen must see and update the actions assigned to them without seeing every finding on the project (Doc 13 §2 "every action should have an owner").                                                                  |

## Definition of Done

- Every acceptance criterion in the nine specs passes.
- **Matrix test** extended with the five new permissions (O-107) at project scope, including company adjustments and the participants rule (T-65).
- **Workflow test:** table-driven over every pair of statuses × every actor kind (owner, collaborator, verifier who is a participant, verifier who isn't, closer, manager, other viewer): exactly the moves in `ACTION_WORKFLOW` succeed, every other returns `ACTION_TRANSITION_NOT_ALLOWED` or `403`.
- **Due-state test:** `actionDueState` at the edges (due today, tomorrow, in 3 and 4 days, yesterday) in two company time zones; the `actions.due` job sends each reminder once across repeated runs and keeps listing Critical overdue actions daily.
- **Numbering test:** 20 actions created concurrently in one project get 20 distinct consecutive numbers; a failed create uses no number.
- **Notification tests:** every event in PLT-23 § Notifications creates exactly the listed recipients, never the actor, never a user who can't view the action.
- **Timeline tests:** every action change writes one entry with old and new values on the project timeline and the action's History; UPDATE and DELETE on `action_update` fail.
- Integration tests for each new endpoint against the local runtime, including read-only mode, archived and on-hold projects, another company's or project's ids, file limits, and a place in use refusing deletion.
- Browser check in **Arabic and English** at phone width: Safety Officer creates a High action on RMX-02 at Block A, owned by a Site Engineer, due in two days → Site Engineer (other browser) sees "You were assigned RMX-02-ACT-0001", starts it, adds a progress note with a photo, comments, tries to complete without evidence (refused), adds evidence and completes → Safety Officer sees "Verification needed", sends it back with a reason → Site Engineer completes again → HSE Manager verifies by site visit and closes → the action is read-only, the comment box is gone, "Create follow-up action" works → the timeline and History show every step.
- `npm run check` and `npm run build` pass; migrations apply to a fresh local D1 and on top of the Sprint 7 data.
- `03_DATABASE.md`, `04_API.md`, `modules/README.md` and `platform/README.md` are updated.
