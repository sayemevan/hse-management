# Sprint 6 — Project Structure & Platform Services

**Status: DONE — accepted by the Product Owner on 2026-11-13 (D-48).** Approved by the Product Owner on 2026-11-12 (D-46), including technical decisions T-38 to T-46 and the proposed answers to open points O-56 to O-70 (D-47). O-56 answers **Q-17**.

## Goal

A project gets its inside: **Areas → Locations → Work Zones** (Doc 06 §5–7), so that every inspection, permit and safety event from Sprint 8 onwards can say exactly where it happened. Project Managers can build their own project team from the project page, without giving anyone more access than they hold. Three shared platform services arrive before the operational modules that need them: **in-app notifications** (one service for every module, Master Rules §6), an **activity timeline** (Doc 04 §12, Doc 08 §12) and the **current project context** with a project switcher in the header (Doc 06 §12, O-55).

## Technical decisions (proposed)

| ID   | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                     | Why                                                                                                                                                                                                                   |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| T-38 | **One `place` table** for Areas, Locations and Work Zones: `level` (`area`, `location`, `work_zone`), `parent_id`, `project_id`. The service enforces the three fixed levels (an area has no parent, a location's parent is an area, a work zone's parent is a location). Later records store **three nullable columns** `area_id`, `location_id`, `work_zone_id`, filled consistently from the chosen place by the shared `PlaceDirectory`. | One set of rules, one picker and one API for all three levels; a fourth level (Doc 06 §15 "Buildings") is a new `level` value, not a new table. Three columns on records keep "filter by Area" a plain indexed query. |
| T-39 | Places are **deactivated, not deleted**, once anything uses them. A place with no children and no use can be deleted. Later modules register a `PlaceUsage` checker in `project`'s contract (`countRecordsUsing(placeId)`); in this sprint the only "use" is having children.                                                                                                                                                                | Old inspections and permits must keep showing where they happened (Doc 06 §13, Doc 08 §17 "deleting is prohibited if records exist"), while mistakes made during set-up can still be removed.                         |
| T-40 | A new **`notification` platform service** with one `notification` table for every module (Doc 04 §13). A notification stores a **type** from a typed registry, its **parameters** (JSON) and a link to the record (`entity_type`, `entity_id`, `project_id`); the text is rendered **in the reader's language when it is shown**, from i18n keys. Notifications are written in the same `UnitOfWork` as the change that causes them.         | No module builds its own notifications (Master Rules §6); a user who switches to Arabic sees old notifications in Arabic too; a failed change never leaves a notification behind.                                     |
| T-41 | Recipients are chosen **when the event happens** from the permission resolver (only people who can see the record, Doc 31 rule 1), and access is **checked again when the notification is opened**: a link to a record the reader can no longer see opens "You no longer have access to this". The actor never notifies themselves.                                                                                                          | Access can change after the notification was written (T-32).                                                                                                                                                          |
| T-42 | The web app gets the **unread count by polling** `GET /notifications/unread-count` every 60 seconds while the tab is visible, and immediately when the tab regains focus. No WebSocket or push in Phase 1.                                                                                                                                                                                                                                   | Workers and D1 have no cheap fan-out; one indexed count per minute per open tab is small. Push notifications are out of Phase 1 scope (Doc 31).                                                                       |
| T-43 | A new **`activity` platform service** with one immutable `activity_entry` table (database triggers reject UPDATE and DELETE, as for `audit_log`). Each entry: who, what (a typed action), when, the record, the project, **old and new values** of the changed fields, and a **snapshot of names** (for example the area name at the time). Written in the same `UnitOfWork` as the change. It is **separate from the audit log**.           | The timeline is shown to users, filtered by permission and translated; the audit log is for security review, keeps request facts and redacted payloads, and is never shown in project screens.                        |
| T-44 | Sprint 5 projects get their timeline **back-filled once by migration** from `audit_log` (`project.created`, `project.updated`, `project.status_changed`, `project.archived`, `project.restored`, `user.project_role.*`).                                                                                                                                                                                                                     | Existing projects don't start with an empty timeline; the audit log already holds every change.                                                                                                                       |
| T-45 | The **current project** lives in the URL: project pages and every later module page are under `/projects/{id}/…` (web) and project-owned API routes are under `/api/v1/projects/{projectId}/…`. The header switcher only navigates; the last project opened is remembered per user on the server (`user_preference.last_project_id`) so "Home" can offer "Continue in {project}".                                                            | Links in notifications and shared URLs always open the right project; no hidden client state can make a user record a hazard in the wrong project.                                                                    |
| T-46 | Member management reuses the **`access` module's project-role service** from US-008 (same rows, same rules, same audit actions). The project-side routes add one check, the **"no more than you hold" rule** (O-46): a caller without `users.roles.assign` may only assign, change or remove a project role whose project-scope permissions are all held by the caller on that project.                                                      | One place for role rules; the Members tab and the user page can never disagree.                                                                                                                                       |
