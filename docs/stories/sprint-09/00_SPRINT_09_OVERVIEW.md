# Sprint 9 — Offline Foundation

**Status: IMPLEMENTED — awaiting Product Owner acceptance.** Approved by the Product Owner on 2026-11-27 (D-56), including technical decisions T-66 to T-74 and the proposed answers to open points O-115 to O-131 (D-57). O-115 confirms **Q-26** (already answered by D-11) for the sync layer; O-122 applies **D-20** (conflicts flagged for review).

## Goal

Construction sites lose signal. D-11 makes **inspection and hazard-report capture work offline, including photos, and sync automatically**; D-20 says a conflict is **flagged for review, both versions are kept, the user chooses, nothing is silently overwritten**. Inspections (Sprint 10) and safety events (Sprint 11) can't build that themselves without each inventing their own storage, retry and conflict rules. This sprint builds the **one offline layer** of the platform (Product Book Doc 01 §15, Doc 02 §4 "Offline capable", Master Rules Rule 15 "Offline Awareness"), the way Sprint 8 built the one action engine before its consumers:

- the app is an **installable PWA** whose shell opens without a connection (service worker);
- a **device store** (IndexedDB) keeps the reference data a capture form needs, drafts, queued changes and photos, separated per user;
- an **offline session** lets a signed-in user keep working when the network drops, without storing tokens on the device;
- a **sync queue** sends queued changes and photos in order when the connection comes back, with retries;
- the API accepts **idempotent writes** (an `Idempotency-Key` and client-generated ids), so a change sent twice is applied once;
- **conflicts** are detected by record version, kept on both sides and resolved by the user on a **review screen**;
- a **sync centre** and a header indicator show what is pending, failed or in conflict.

Sprint 9 ships **no offline business form**: everything outside inspection and hazard capture stays online-only (D-11), and inspection is the first consumer in Sprint 10 (O-116).

## Technical decisions (approved, D-56)

| ID   | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | Why                                                                                                                                                                                                                             |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| T-66 | A **hand-written service worker** (`apps/web/src/service-worker/`, TypeScript, bundled to `public/sw.js` by a small build step with esbuild, already in the workspace through Wrangler and Drizzle Kit) with three rules: **hashed static assets** (`/_next/static/*`, fonts, icons) cache-first; **app pages and their RSC payloads** network-first with a 3-second timeout, falling back to the last cached copy and then to an **offline page**; **`/api/*` is never cached by the service worker** (data offline lives in the device store, PLT-26). After sign-in the worker pre-caches the routes that modules mark as offline-capable (T-72). A new version waits and the app offers **Reload** (O-125).                                                                                                                                                                                | No new runtime dependency and full control over what is cached on Next 16 / OpenNext. Caching API responses would keep personal data and permission-dependent answers outside the rules of the device store.                    |
| T-67 | The **device store** is one IndexedDB database per origin (each company subdomain is its own origin, so companies never share a store), opened through **`idb`** (≈1 kB wrapper). Object stores: `meta`, `session`, `reference`, `drafts`, `outbox`, `blobs`, `conflicts`. Every row carries `userId`; the app only reads rows of the signed-in user. A versioned upgrade function migrates the schema; the store is the web app's only offline storage (no `localStorage` for data). **New web dependencies:** `idb` (runtime) and, for the first web unit tests, `vitest` and `fake-indexeddb` (development only).                                                                                                                                                                                                                                                                           | Per-origin isolation matches the tenant model (D-06); one place to clear, migrate and test.                                                                                                                                     |
| T-68 | **Records created offline get their id on the device** (`crypto.randomUUID()`, the same format as `generateId`). Offline-capable create routes accept an optional `id`; the server keeps it if it is a UUID not used before, so photos, items and follow-up changes can refer to the record before it reaches the server. Record **numbers** (T-60) are still given by the server on sync; until then the record shows "Not yet synced".                                                                                                                                                                                                                                                                                                                                                                                                                                                       | References between queued changes need stable ids; numbers must stay gap-free and per project.                                                                                                                                  |
| T-69 | **Idempotent writes**: offline-capable write routes take an **`Idempotency-Key`** header (UUID). A new `idempotency_key` table (`company_id`, `user_id`, `key`, `method`, `route`, `request_hash`, `status_code`, `resource_type`, `resource_id`, `created_at`, `expires_at`) gets its row **in the same `UnitOfWork` batch** as the change (unique on `company_id, key`). A repeat with the same key and the same body **replays** the result (same status, the resource read fresh, header `Idempotent-Replayed: true`); the same key with a different body → `422 IDEMPOTENCY_KEY_REUSED`; two copies racing → the batch of the second fails on the unique index and it replays. Keys expire after **30 days** (O-124), removed by the daily housekeeping job. A `idempotent()` route helper adds this to a route; Sprint 9 applies it to the file upload route and the sync probe (O-116). | The network can drop after the server committed but before the device heard back; a retry must not create a second inspection or photo. Writing the key in the change's batch makes "applied" and "remembered" one atomic fact. |
| T-70 | **Conflicts are detected by version**: offline-capable records get an integer **`version`** (starts at 1, +1 on every change). Offline updates send **`baseVersion`**; if the server's version differs, the update is **not applied** and the API answers **`409 SYNC_CONFLICT`** with the server's current record. Additions that can't overwrite anything (a new record, a new photo, a new note) never conflict. The server also writes a **`sync_conflict`** row (`company_id`, `user_id`, `entity_type`, `entity_id`, `base_version`, `server_version`, `client_payload` JSON, `status` open / resolved / discarded, `resolution`, `resolved_at`), so **both versions are kept** on the server, not only on the device (D-20).                                                                                                                                                            | Record-level versions are simple, cheap in D1 and impossible to bypass; field-level merging is offered in the review screen, not guessed by the server.                                                                         |
| T-71 | **One sync engine** in the web app (`modules/offline/sync-engine.ts`) drains the outbox **in creation order per record** (a record's create before its updates and photos; different records in parallel, at most 3 requests at once). It runs on `online`, on app start and focus, every 60 seconds while items are pending, after each new item, and on **Background Sync** where the browser supports it (Chromium); a **Web Lock** makes sure only one tab syncs. Failures back off 5 s, 15 s, 1 min, 5 min, then every 15 min. Network errors and `5xx`/`429` retry; `401` waits for sign-in (PLT-27); `409 SYNC_CONFLICT` moves the item to conflicts (PLT-30); other `4xx` (validation, permission, archived project) move it to **Needs attention** with the reason (O-123).                                                                                                           | Order matters (a photo can't reach a record that doesn't exist yet); one engine with one rule set is testable; iOS has no Background Sync, so foreground triggers are the baseline.                                             |
| T-72 | **Modules plug in through one web contract**: `registerOfflineEntity({ type, label, routes, toRequest, fromServer, conflictFields, render })` describes a record type that can be captured offline, and `registerReferencePack({ key, load, scope })` describes the reference data it needs on the device (for example the project's places and members). The offline layer never imports a business module. Sprint 9 registers the shared packs (profile, projects the user can view, places) and a **sync probe** used by tests and the development build only (O-116).                                                                                                                                                                                                                                                                                                                      | The same shape as `ActionSource` (T-57): the layer is built before its consumers and they plug in later.                                                                                                                        |
| T-73 | **Offline session without stored tokens**: the access token stays in memory and the refresh token in its cookie (T-1). On each online start the app saves an **offline profile** in the device store (user, company, language, role summary, the permission snapshot for the user's projects, `savedAt`). When the network is down, the app opens on that profile, shows capture screens the snapshot allows, and **queues**; nothing is sent until a live session exists again. **The server re-checks every permission on sync** (T-32); the snapshot only decides what the UI offers.                                                                                                                                                                                                                                                                                                       | Tokens on disk would undo T-1. Sync needs the refresh cookie, which survives offline periods within D-04's limits.                                                                                                              |
| T-74 | **Photos are compressed on the device before they are stored**: re-encoded to JPEG, long edge at most **2,560 px**, quality 0.82, which also removes EXIF metadata including GPS (O-121). The original is not kept. Blobs live in the `blobs` store, linked to their outbox item; they upload through the file route of the owning module with an `Idempotency-Key` (T-69) and the record id (T-68). Uploads count against the plan's storage on arrival (D-28).                                                                                                                                                                                                                                                                                                                                                                                                                               | A 12-megapixel phone photo is 4–8 MB; compressed it is ≈0.5–1 MB, which keeps device storage and slow-site uploads manageable, and the server limits (≤ 10 MB) are met.                                                         |

## Definition of Done

- Every acceptance criterion in the seven specs passes.
- **Idempotency tests** (API integration): the same create sent twice → one record, one audit entry, second answer replayed; same key with another body → `IDEMPOTENCY_KEY_REUSED`; 10 parallel copies → one record; keys of one company invisible to another; expired keys removed by the job.
- **Conflict tests** (API): an update with an old `baseVersion` changes nothing, returns `SYNC_CONFLICT` with the server copy and writes one `sync_conflict` row; Keep mine, Keep theirs and Combine each end with the expected version and audit entries; a second resolve → `SYNC_CONFLICT_RESOLVED`; another user's conflict → `404`.
- **Sync engine tests** (web, Vitest with `fake-indexeddb`): ordering per record, parallel limit, back-off schedule, each response class routed to the right state (retry, wait for sign-in, conflict, needs attention, waiting read-only), one tab syncing under a Web Lock, a different user's rows never read.
- **Photo test**: a 4000 × 3000 JPEG with GPS EXIF is stored ≤ 2,560 px on its long edge without EXIF.
- Read-only route review (PLT-11) lists the new writes; conflict resolution is blocked in read-only mode.
- Browser check in **Arabic and English** at phone width (development build, the demo company): sign in → install prompt offered → sync probe: create with two photos **offline** (DevTools offline) → indicator "Offline · 1 pending" → reload while offline: the app shell and the probe form open, an online-only page shows the offline page → back online: the item syncs, photos upload once, indicator returns to Online → edit the probe offline while another browser changes it online → back online: conflict appears, the review shows both versions, Combine resolves it → sign out with an item pending: the dialog offers the three choices → sign in again as the same user: the item syncs.
- `npm run check` and `npm run build` pass; the production build contains no sync probe route or screen; migrations apply to a fresh local D1 and on top of the Sprint 8 data.
- Lighthouse PWA "installable" checks pass for the production build.
- `03_DATABASE.md`, `04_API.md`, `platform/README.md` and a new `apps/web/src/modules/offline/README.md` (how a module registers an offline entity) are updated.
