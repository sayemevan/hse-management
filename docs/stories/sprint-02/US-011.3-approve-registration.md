# US-011.3 — Approve a Registration

| Field    | Value                                                                                    |
| -------- | ---------------------------------------------------------------------------------------- |
| Epic     | Epic 02 — Company Management                                                             |
| Priority | Must                                                                                     |
| Status   | Approved                                                                                 |
| Sources  | Product Book Doc 06 §2 (platform manages companies), Doc 08; D-06, D-29, D-32; T-8, T-14 |

## Business Goal

Let the System Owner check each application and turn it into a working company, with its subdomain, a 14-day trial and a Company Administrator, in one step.

## Description

The System Owner sees a queue of submitted applications, opens one, confirms the phone number by hand (D-32), may correct the plan, and approves it. The approval creates everything the company needs and emails the applicant a sign-in link.

## Actors

System Owner.

## Preconditions

- Signed in on the base domain as a System Owner.
- The application has status `submitted`.

## User Flow

1. Open **Registrations** in the platform console. The queue shows submitted applications, oldest first, and can be filtered by status.
2. Open an application: company details, subdomain, applicant, phone, plan, submission date, and the review history (US-011.4/011.5).
3. Call or message the applicant to confirm the phone number, then tick **I have confirmed the phone number**.
4. Optionally change the plan.
5. Select **Approve**, and confirm.
6. See "Company created" with a link to the new subdomain.

## Functional Requirements

The system shall, in one atomic batch:

1. Re-check that the subdomain is still free and the applicant email is still unused. If not, approval fails with a clear message and nothing changes.
2. Create the `company` (status `active`, with the application's name, slug, country, city, time zone, default language and contact details).
3. Create the `subscription` (PLT-06: `trial`, 14 days from now).
4. Create the `user` (status `active`, email verified, `password_hash` from the application, language from the application) and a `user_role` of `company_administrator` at company scope.
5. Record the decision in `registration_review` (approved, by whom, the phone-confirmed flag, any plan change) and set the application to `approved` with `company_id`.
6. Enqueue `registration.approved` to the applicant, containing the sign-in link `https://<slug>.<base-domain>/login`.
7. Audit `registration.approved` and `company.created`.
8. Clear the tenant cache entry for the slug (PLT-02), so the new subdomain works immediately.

## Validation Rules

- `phoneConfirmed` must be `true`.
- The plan, if changed, must be an active plan.
- The application must be `submitted`. Approving twice, or approving a rejected application, is refused (`409 CONFLICT`).

## Permission Rules

`platform.registrations.approve`, granted to the System Owner by the temporary checker (T-14). Base domain only. Everyone else gets 403.

## Database Impact

Inserts `company`, `subscription`, `user`, `user_role`, `registration_review`, `email_outbox` and `audit_log` rows; updates `company_registration`. `company` gains `country_code`, `city`, `contact_email` and `contact_phone`.

New table `registration_review`:

| Column                                | Type              | Notes                     |
| ------------------------------------- | ----------------- | ------------------------- |
| `id`                                  | TEXT (UUID)       | PK                        |
| `registration_id`                     | TEXT              | FK                        |
| `decision`                            | TEXT              | `approved`, `rejected`    |
| `reason`                              | TEXT, nullable    | required for rejection    |
| `phone_confirmed`                     | INTEGER (boolean) |                           |
| `previous_plan_code`, `new_plan_code` | TEXT, nullable    | when the plan was changed |
| `decided_by`, `decided_at`            | TEXT / INTEGER    |                           |

## API Requirements

- `GET /api/v1/platform/registrations?status=submitted&page=1&pageSize=20` → paginated list
- `GET /api/v1/platform/registrations/{id}` → details plus review history (never the password hash)
- `POST /api/v1/platform/registrations/{id}/approve` with `{ phoneConfirmed: true, planCode? }` → `{ companyId, slug, signInUrl }`

## UI Requirements

- The console is reachable from the System Owner's home page; on mobile, the queue is shown as cards.
- The detail page follows Doc 05 §17 (overview, information, history).
- **Approve** is disabled until the phone checkbox is ticked; it asks for confirmation (it creates a tenant).
- Empty queue: "No applications are waiting for review."

## Error Handling

| Situation                                 | Message                                                                                                          |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Subdomain or email taken since submission | "The subdomain or email is no longer available. Reject the application and ask the applicant to choose another." |
| Already decided                           | "This application has already been decided."                                                                     |
| Phone not confirmed                       | Field error on the checkbox                                                                                      |

## Notifications

`registration.approved` to the applicant (in their language).

## Audit Requirements

`registration.approved` (actor: System Owner; new value: plan, phone confirmed) and `company.created` (entity: the company).

## Acceptance Criteria

- Approval creates the company, trial, administrator and role together, or nothing at all.
- The applicant can sign in on the new subdomain with the password from their application immediately afterwards.
- Non-System Owners can't list, view or approve applications.
- Approving twice is refused.

## Test Scenarios

- **Positive:** approve; approve with a plan change; sign in on the new subdomain.
- **Negative:** phone not confirmed; company user or anonymous caller (403/401); already approved; slug taken meanwhile; called on a company subdomain.

## Future Improvements

Payment-proof review (Sprint 4); Commercial Registration checks; assigning applications to individual reviewers.
