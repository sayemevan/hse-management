# US-011.2 — Verify Registration Email

| Field    | Value                                                            |
| -------- | ---------------------------------------------------------------- |
| Epic     | Epic 02 — Company Management                                     |
| Priority | Must                                                             |
| Status   | Approved                                                         |
| Sources  | Product Book Doc 16 (Email Verification); D-32; O-15, O-18; T-10 |

## Business Goal

Make sure the applicant controls the email address before anyone spends time reviewing the application (D-32: email is the only automatic check).

## Description

The verification email contains a single-use link. Opening it marks the email as verified and submits the application to the System Owners' review queue.

## Actors

Applicant.

## Preconditions

An application in `pending_email_verification` with an unexpired token.

## User Flow

1. Open the link from the email (`<base>/register/verify?token=…`).
2. See **Email verified — your application has been sent for review**, with what happens next and roughly how long it takes.
3. Receive a confirmation email (`registration.submitted`).

If the link is old or used: see **This link has expired**, with a form to request a new one.

## Functional Requirements

The system shall:

1. Accept the token through `POST` (the page posts it). The link itself never changes data on `GET`, so email scanners that open links can't trigger verification by accident.
2. Consume the token atomically: mark it used, set `email_verified_at` and `submitted_at`, and change the status to `submitted`, all in one batch. A token works only once.
3. Enqueue `registration.submitted` to the applicant and `registration.new_for_review` to every active System Owner (O-18), in the same batch.
4. Provide **Resend verification email**: it accepts an email address, always answers the same way, and only when an unverified application exists does it invalidate the old token and send a new one. It is limited to 3 per application per hour, plus the per-IP limit.
5. Treat an already-verified application as a success, showing the "sent for review" message, so a second click isn't an error.

## Validation Rules

- The token must exist, have purpose `registration_email`, be unused and be unexpired.
- The resend email must be a valid address.

## Permission Rules

Anyone with the link (the token is the credential). Base domain only.

## Database Impact

Updates `one_time_token` and `company_registration`; inserts `email_outbox` rows.

## API Requirements

- `POST /api/v1/registrations/verify-email` with `{ token }` → `{ status: 'submitted' }`, or the error `TOKEN_INVALID_OR_EXPIRED`
- `POST /api/v1/registrations/resend-verification` with `{ email }` → `202`, always the same body

## UI Requirements

- Verifying: spinner and "Checking your link…".
- Success: check icon, a short explanation, and a link to the platform home.
- Expired: explanation plus the email field and **Send a new link**.
- Arabic and English, phone width.

## Error Handling

| Situation                     | Message                                                                 |
| ----------------------------- | ----------------------------------------------------------------------- |
| Invalid, used or expired link | "This link has expired or was already used. Request a new one below."   |
| Resend requested              | "If an application is waiting for this address, we've sent a new link." |

## Notifications

`registration.submitted` (applicant), `registration.new_for_review` (System Owners), and a new `registration.verify_email` on resend.

## Audit Requirements

`registration.email_verified` (actor null; the registration id).

## Acceptance Criteria

- A valid link submits the application exactly once and notifies all System Owners.
- Opening the page without the POST changes nothing.
- An expired or used link shows the recovery form, and a new link works.
- Resend never reveals whether an application exists.

## Test Scenarios

- **Positive:** verify; verify twice (second time also shows success); resend and then verify with the new link.
- **Negative:** expired token (24 h + 1 min); token of another purpose; old token after a resend; resend rate limit.

## Future Improvements

A verification code as an alternative to the link (for phones where links open in another browser).
