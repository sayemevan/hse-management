# US-011.1 — Register a Company

| Field    | Value                                                                                                                                            |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Epic     | Epic 02 — Company Management                                                                                                                     |
| Priority | Must                                                                                                                                             |
| Status   | Approved                                                                                                                                         |
| Sources  | Product Book Doc 08 §1 ("Register their company"), §3 (company profile); D-06, D-08, D-16, D-17, D-29, D-32; O-12 to O-17, O-19; T-8, T-10, T-11 |

## Business Goal

Let a construction or industrial company apply for the platform by itself, with its own subdomain, without contacting sales first (D-06).

## Description

On the base domain, the applicant fills in one form with the company's details, their own details as the future Company Administrator, a plan, and a password. After submitting, they receive a verification email (US-011.2). The application reaches the System Owner only once the email is verified.

## Actors

Applicant (a prospective Company Administrator; not signed in).

## Preconditions

- The visitor is on the base domain (platform context).
- The applicant's email is not already used by a user or by an open application (D-08).

## User Flow

1. Open **Register your company** (`<base>/register`), for example from the login page link.
2. Enter company details: company name, subdomain (checked live), country, city, time zone (pre-filled from the country), default language.
3. Enter administrator details: full name, work email, mobile number, password and its confirmation.
4. Choose a plan (Basic / Pro / Enterprise).
5. Tick "I accept the Terms of Service and Privacy Policy" (O-14).
6. Pass the bot check (Turnstile, T-11) and select **Submit application**.
7. See **Check your email**, with the email address shown and a "Resend email" button.

## Functional Requirements

The system shall:

1. Check subdomain availability as the applicant types (debounced). It is unavailable if it is taken by a company or reserved by an open application (O-16), or if it breaks the D-16 rules. Subdomains are suggested from the company name.
2. Verify the Turnstile token on the server before anything else (T-11).
3. Re-validate every field on the server, including availability, and reject the request if anything changed.
4. Hash the password (the Sprint 1 hasher) and never store or log it in plain text.
5. Create a `company_registration` with status `pending_email_verification`, a verification token (T-10, valid for 24 hours, configurable) and an enqueued `registration.verify_email` email, all in one batch.
6. Record the applicant's interface language and use it for all their emails (O-19).
7. Respond the same way whether or not the email is already in use, to avoid revealing accounts. If it is in use, the email sent says so instead of containing a verification link, and no application is created.
8. Rate-limit submissions and availability checks per IP (T-7 binding, separate buckets).
9. Remove applications that are still unverified after 7 days, along with their tokens (O-15), with a daily job; this releases the subdomain.

## Validation Rules

| Field            | Rule                                                                                                                     |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Company name     | Required, 2–150 characters, trimmed                                                                                      |
| Subdomain        | D-16: 3–30 characters, `a–z 0–9 -`, no leading or trailing hyphen, not reserved; available                               |
| Country          | Required ISO 3166-1 alpha-2 code from the list (O-17)                                                                    |
| City             | Required, 2–100 characters                                                                                               |
| Time zone        | Required IANA time zone                                                                                                  |
| Default language | `en` or `ar`                                                                                                             |
| Full name        | Required, 2–150 characters                                                                                               |
| Work email       | Required, valid, at most 254 characters, lowercased                                                                      |
| Mobile number    | Required, international format (`+` and 8–15 digits); Saudi numbers may be typed as `05…` and are normalised to `+9665…` |
| Password         | D-03 policy; must match the confirmation                                                                                 |
| Plan             | An active plan code (PLT-06)                                                                                             |
| Terms            | Must be accepted                                                                                                         |
| Bot check        | Turnstile token valid                                                                                                    |

## Permission Rules

Anyone on the base domain. Not available on company subdomains (404).

## API Requirements

- `GET /api/v1/registrations/slug-availability?slug=acme` → `{ slug, available, reason?: 'invalid' | 'reserved' | 'taken' }`
- `POST /api/v1/registrations` with all form fields plus `turnstileToken` → `202 Accepted`, always with the same body `{ email }`

## UI Requirements

- One page with three clearly titled sections (Company, Administrator, Plan), mobile first, grouped fields (Doc 05 §7).
- The subdomain field shows the full address (`acme.<base-domain>`) and an availability badge (icon + text).
- Password field with show/hide and the live policy checklist (reused from US-005).
- Plan cards (PLT-06), with "Price on request" while prices are unknown.
- Inline validation, required markers, and one primary button (Doc 05 §15).
- **Check your email** page: the address, "didn't get it?" help, and **Resend email** (US-011.2).
- Fully translated; RTL in Arabic; the subdomain and email fields are left-to-right.

## Error Handling

| Situation             | Message                                                     |
| --------------------- | ----------------------------------------------------------- |
| Subdomain unavailable | "This address is already taken. Try another."               |
| Bot check failed      | "We couldn't confirm you're not a robot. Please try again." |
| Too many attempts     | Rate-limit message (Sprint 1)                               |
| Any field invalid     | Field-level messages                                        |
| Server unavailable    | Standard network message                                    |

## Notifications

`registration.verify_email` to the applicant, or an "account already exists" email if the email is in use.

## Audit Requirements

`registration.created` (actor null; the IP is recorded). The password and token are never included.

## Acceptance Criteria

- A valid submission creates one pending application and sends one verification email in the applicant's language.
- A taken or reserved subdomain is rejected, both live and on submit.
- An email that is already in use gets the same response, but no application.
- A failed bot check creates nothing.
- Unverified applications disappear after 7 days, and their subdomain becomes available again.
- The form works at phone width in Arabic and English.

## Test Scenarios

- **Positive:** a full valid submission; a Saudi `05…` number normalised; time zone pre-filled for SA.
- **Negative:** each validation rule; reserved slug; a slug held by a pending application; an email belonging to an existing user; an invalid Turnstile token; rate limited; called from a company subdomain.
- **Boundary:** 3- and 30-character subdomains; company name of 2 and 150 characters; 151 rejected.

## Future Improvements

Commercial Registration and VAT details (not required, D-19/D-32); SMS phone verification; custom domains (D-06).
