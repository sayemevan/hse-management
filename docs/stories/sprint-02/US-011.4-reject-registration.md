# US-011.4 — Reject a Registration

| Field    | Value                        |
| -------- | ---------------------------- |
| Epic     | Epic 02 — Company Management |
| Priority | Must                         |
| Status   | Approved                     |
| Sources  | D-31; O-15, O-16; T-10       |

## Business Goal

Let the System Owner turn down an application that can't be approved yet, telling the applicant exactly why, so they can fix it (D-31).

## Description

From the application detail page, the System Owner selects **Reject** and writes a reason. The applicant receives the reason and a link to correct and resubmit the same application (US-011.5).

## Actors

System Owner.

## Preconditions

Signed in as a System Owner; the application has status `submitted`.

## User Flow

1. On the application detail page, select **Reject**.
2. Write the reason (required) in a dialog, for example "The phone number didn't answer; please provide a reachable number."
3. Confirm.
4. The application leaves the "submitted" queue and shows as rejected, with the reason in its history.

## Functional Requirements

The system shall, in one batch:

1. Record a `registration_review` with decision `rejected`, the reason, the reviewer and the time.
2. Set the application to `rejected`.
3. Create a resubmission token (T-10, purpose `registration_resubmit`, valid for 30 days, O-15).
4. Enqueue `registration.rejected` to the applicant, containing the reason and the resubmission link.
5. Keep the subdomain reserved while the application can still be resubmitted (O-16).
6. After 30 days without resubmission, a daily job sets the application to `closed`, invalidates its token and releases the subdomain (O-15). The record and its history are kept.

## Validation Rules

- Reason: required, 10–1000 characters, trimmed.
- The application must be `submitted`.

## Permission Rules

`platform.registrations.reject` (System Owner, T-14). Base domain only.

## Database Impact

Inserts `registration_review`, `one_time_token`, `email_outbox` and `audit_log` rows; updates `company_registration`.

## API Requirements

`POST /api/v1/platform/registrations/{id}/reject` with `{ reason }` → `{ status: 'rejected' }`

## UI Requirements

- **Reject** is a secondary, danger-styled button next to Approve.
- A dialog with a multi-line reason field, a character counter, and a note that the applicant will see this text.
- Rejected applications show the reason in the history list.

## Error Handling

| Situation        | Message                                                                      |
| ---------------- | ---------------------------------------------------------------------------- |
| Reason too short | "Explain the reason in at least 10 characters — the applicant will read it." |
| Already decided  | "This application has already been decided."                                 |

## Notifications

`registration.rejected` to the applicant, in their language. The reason is shown exactly as written; it isn't translated.

## Audit Requirements

`registration.rejected` (actor: System Owner; new value: the reason).

## Acceptance Criteria

- Rejection requires a reason and emails it, with a working resubmission link.
- The subdomain stays reserved for 30 days, and is released when the application is closed.
- The history keeps every rejection.

## Test Scenarios

- **Positive:** reject; reject again after a resubmission (two entries in the history).
- **Negative:** reason of 9 characters; 1001 characters; already approved; not a System Owner.
- **Boundary:** a closed application after 30 days + 1 minute; the subdomain is free again.

## Future Improvements

Predefined rejection reasons; asking for specific fields to be corrected.
