# Document 00 — Vision & Product Foundation

**Version:** 1.0

---

# 1. Vision

Build a modern, cloud-native, AI-first Safety Operations Platform that helps construction and industrial companies manage all daily **HSE** operations from one centralized system.

The platform replaces paper forms, spreadsheets, disconnected applications and manual communication with one integrated solution.

This product is designed to become the daily operating system for Safety Officers, Supervisors, Engineers, Project Managers and **HSE** Managers.

- Construction

- Industrial Projects

---

- Bahrain

# 3. Product Philosophy

This product is **NOT** designed to be:

- An Excel replacement
- A document storage system
- A reporting-only application
- An **ERP** system

A Safety Officer should start the day with this platform and finish the day with this platform.

# Document 01 — System Architecture

**Version:** 1.0

---

# 1. Architecture Philosophy

The platform must follow a modern cloud-native architecture.

Every module should be independent, reusable and scalable.

The architecture should support future growth without major rewrites.

---

# 2. Design Principles

The architecture must follow these principles.

- Modular
- Scalable
- Serverless First
- **API** First
- Mobile First
- Cloudflare First
- AI Friendly
- Secure by Default

---

# 3. High-Level Architecture

``` Users

↓

Progressive Web App (**PWA**)

↓

**API** Layer

↓

### Business Logic Layer

↓

### Data Access Layer

↓

Database & Storage

↓

### Cloudflare Infrastructure

```

Each layer has a single responsibility.

No layer should directly access another non-adjacent layer.

---

# 4. Application Layers

## Presentation Layer

Responsible for:

- User Interface
- Forms
- Validation
- Navigation
- Responsive Design

This layer must never contain business logic.

---

## API Layer

Responsible for:

- Authentication
- Request Validation
- Authorization
- Routing
- Response Formatting

No business rules should exist here.

---

## Business Layer

Responsible for:

- Business Rules
- Workflow
- Permission Checks
- Calculations
- Automation

This is the heart of the system.

---

## Data Layer

Responsible for:

- Database Operations
- Query Optimization
- Transactions
- Storage Access

No UI logic is allowed.

---

# 5. Module Architecture

Every module must be independent.

Example modules:

- Company
- Project
- Users
- Inspection
- Hazard
- Incident
- Permit
- **PPE**
- Training
- Reports

Each module owns its own business logic.

Modules communicate only through well-defined services.

---

# 6. Shared Components

The following components should be reusable across the entire system.

- Authentication
- File Upload
- Notifications
- Search
- Filters
- Comments
- Attachments
- Activity Timeline
- Audit Log

No module should create duplicate functionality.

---

# 7. File Storage Strategy

Large files must never be stored inside the database.

Examples:

- Images
- Videos
- PDFs
- Certificates
- Attachments

Only metadata and storage references should be saved in the database.

---

# 8. Database Strategy

The application should support database abstraction.

Business logic must not depend on a specific database engine.

This allows future migration without changing application behavior.

---

# 9. Multi-Company Architecture

One platform serves multiple companies.

Each company owns:

- Users
- Projects
- Employees
- Inspections
- Hazards
- Reports

Data isolation between companies is mandatory.

A user can only access data belonging to their authorized company.

---

# 10. Multi-Project Architecture

A company can create multiple projects.

Every operational record belongs to one project.

Examples:

- Inspection
- Incident
- Permit
- Hazard
- Toolbox Talk
- Corrective Action

Project-level filtering must be available throughout the platform.

---

# 11. Security Principles

Every request must be authenticated.

Every action must be authorized.

Every data modification must be logged.

Sensitive operations should require additional verification when appropriate.

---

# 12. Audit Trail

The system must automatically record important activities.

Examples:

- Created
- Updated
- Deleted
- Approved
- Rejected
- Closed
- Reopened

Each log should include:

- User
- Date & Time
- Project
- Previous Value
- New Value

Audit history should not be editable.

---

# 13. Notification Architecture

The notification system should support multiple channels.

Current:

- In-App Notifications

Future:

- Email
- **SMS**
- WhatsApp
- Push Notifications

The notification engine should be reusable across all modules.

---

# 14. Reporting Architecture

Reports should be generated directly from structured data.

No report should depend on manual formatting.

Every report should support future export to:

- **PDF**
- Excel
- **CSV**

---

# 15. Offline Strategy

The application should continue basic operations when internet connectivity is unstable.

Examples:

- Create Inspection
- Capture Photos
- Record Hazard

Data should synchronize automatically when the connection is restored.

---

# 16. Performance Goals

Target performance objectives:

- Initial page load under 2 seconds.
- **API** response under **500** milliseconds for standard operations.
- Support thousands of records without noticeable slowdown.
- Optimize for mobile devices used on construction sites.

---

# 17. Future Scalability

The architecture should allow new modules to be added without changing existing modules.

Examples of future modules:

- Environmental Management
- Equipment Inspection
- Medical
- Emergency Response
- Compliance
- AI Assistant
- Quality Management
- Asset Management

The platform should evolve through modular expansion rather than architectural redesign.

# Document 04 — Database Design Principles

**Version:** 1.0

---

# Purpose

This document defines the database philosophy and data modeling standards for the platform.

It ensures that every module follows one consistent database design approach.

All future database structures must comply with this document.

---

# 1. Database Philosophy

The database is the single source of truth.

Every business operation must be backed by structured, normalized and reliable data.

The database should be designed for long-term maintainability rather than short-term convenience.

---

# 2. Database Principles

Every table must have a clear business purpose.

Avoid duplicate data.

Avoid unnecessary relationships.

Store business data only once.

Reference it everywhere else.

---

# 3. Naming Convention

Use singular names.

Examples:

- company
- project
- employee
- inspection
- hazard
- incident
- permit

Avoid abbreviations.

Table and column names must clearly describe their purpose.

---

# 4. Primary Keys

Every table must contain a unique identifier.

The identifier should never change during the record's lifetime.

Primary keys must not contain business meaning.

---

# 5. Foreign Keys

Relationships should be explicit.

Every reference between tables must be clearly defined.

Orphan records should never exist.

---

# 6. Standard Audit Fields

Every business table should include standard audit information.

Recommended fields include:

- Created By
- Created At
- Updated By
- Updated At

For modules that support soft deletion:

- Deleted By
- Deleted At

These fields provide accountability and traceability.

---

# 7. Status Management

Avoid using multiple boolean flags to represent business states.

Instead, use a single status field with clearly defined values.

Example lifecycle:

Draft → Submitted → Under Review → Approved → Closed

The exact status values will be defined by each module.

---

# 8. Soft Delete Policy

Business records should normally be soft deleted.

Deleting a record should not remove historical information unless explicitly required.

This preserves audit history and supports recovery.

---

# 9. Attachments

Files must never be stored inside the database.

The database should store only:

- File reference
- File name
- File type
- File size
- Storage location

Actual files belong in object storage.

---

# 10. Images

Inspection photos, hazard images and incident evidence should be linked to their parent records.

A business record may have multiple images.

Images should remain accessible even if additional photos are added later.

---

# 11. Comments

Comments should be designed as reusable entities.

Any module should be able to receive comments without creating separate comment systems.

Examples:

- Hazard
- Incident
- Inspection
- Corrective Action

---

# 12. Activity Timeline

Every important business object should support an activity timeline.

Timeline entries may include:

- Created
- Updated
- Assigned
- Approved
- Closed
- Reopened

This provides a complete operational history.

---

# 13. Notifications

Notification records should be generic.

The notification system must support every module without requiring module-specific notification tables.

---

# 14. Multi-Company Design

Every business record must belong to a company.

Cross-company data access is prohibited.

Data isolation is mandatory.

---

# 15. Multi-Project Design

Operational records should belong to a specific project whenever applicable.

Examples:

- Inspection
- Permit
- Hazard
- Incident
- Corrective Action

This enables project-level reporting and filtering.

---

# 16. User Relationships

Business records should reference users by identifier rather than storing duplicated user information.

This ensures consistency when user details change.

---

# 17. Historical Records

Important historical events should never be overwritten.

Where appropriate, maintain history instead of replacing previous values.

Examples include approvals, assignments and status changes.

---

# 18. Scalability

Database design must support:

- Millions of records
- Thousands of concurrent users
- Large numbers of projects
- Large numbers of uploaded files

No design decision should assume small data volumes.

---

# 19. Future Expansion

The database should allow future modules without redesigning existing structures.

Examples:

- Environmental Management
- Equipment Inspection
- Medical
- Compliance
- Asset Management
- AI Recommendations

Future tables should integrate naturally into the existing data model.

---

# 20. AI Database Rules

When generating database structures, AI assistants must:

- Reuse existing entities whenever appropriate.
- Avoid duplicate tables.
- Keep relationships simple.
- Normalize data where practical.
- Preserve historical information.
- Prefer extensibility over shortcuts.
- Never break existing schema without a migration plan.

---

# Final Principle

A well-designed database should remain stable even as new features are introduced.

Modules may evolve.

User interfaces may change.

Technologies may change.

The database foundation should remain reliable, consistent and scalable for the lifetime of the product.

# Document 07 — Identity, Roles & Permission System

**Version:** 1.0

---

# Purpose

This document defines how users, roles, permissions and access control work throughout the platform.

The permission system must remain flexible enough to support companies of all sizes while maintaining strong security and simplicity.

---

# 1. Design Philosophy

Access control is based on three independent concepts:

- Identity
- Role
- Permission

A user's identity determines **who they are**.

A role describes **their responsibility**.

Permissions define **what they are allowed to do**.

These concepts must remain independent.

---

# 2. Access Model

The platform follows:

**Identity → Role → Permission → Scope**

Every authorization decision must pass through all four layers.

---

# 3. Identity

Each user has one unique account.

A user should never create multiple accounts simply because they work on different projects.

The same identity may belong to multiple companies (future) or multiple projects.

---

# 4. Roles

Roles represent job responsibilities.

Examples include:

- Company Administrator
- **HSE** Director
- **HSE** Manager
- Project Manager
- Safety Officer
- Site Engineer
- Supervisor
- Foreman
- Worker
- Client
- Consultant
- Auditor

Roles describe responsibilities only.

They do not automatically grant unlimited permissions.

---

# 5. Permissions

Permissions define specific actions.

Examples:

- Create Inspection
- Edit Inspection
- Delete Inspection
- Approve Inspection
- Create Permit
- Approve Permit
- Close Permit
- View Incident
- Export Reports
- Manage Users
- Manage Projects

Every permission should represent one action.

Avoid combining multiple actions into a single permission.

---

# 6. Scope

Permissions are always evaluated within a scope.

Supported scopes include:

- Platform
- Company
- Project
- Area (Future)
- Location (Future)

Example:

A Safety Officer may edit inspections only inside Project Alpha.

The same user may have read-only access in Project Beta.

---

# 7. Permission Strategy

Prefer granting the minimum permissions required.

Users should receive only the access necessary to perform their responsibilities.

Avoid broad administrative privileges.

---

# 8. Role Assignment

Users may hold different roles in different projects.

Example:

Project A

### Safety Officer

Project B

Supervisor

Project C

### Read Only Auditor

The platform must support independent role assignments.

---

# 9. Permission Categories

Permissions should be grouped by module.

Examples:

Dashboard

Company

Projects

Employees

Inspection

Hazards

Incidents

Permits

Reports

Administration

This simplifies administration as the platform grows.

---

# 10. Approval Permissions

Approval actions require dedicated permissions.

Examples:

### Approve Inspection

### Approve Permit

### Approve Incident Closure

### Approve Corrective Action

Approval rights should never be implied by edit permissions.

---

# 11. Read Access

Viewing data is independent from editing data.

Possible combinations include:

### View Only

View + Create

View + Edit

View + Approve

### Full Management

---

# 12. Temporary Access

The platform should support temporary access.

Examples:

### External Auditor

Consultant

### Client Representative

Temporary permissions should expire automatically.

---

# 13. Account Status

Supported user statuses:

- Pending Invitation
- Active
- Suspended
- Locked
- Archived

Suspended users must immediately lose system access.

---

# 14. Authentication

Every request requires authentication.

Future authentication methods may include:

- Email & Password
- Google
- Microsoft
- Single Sign-On (Enterprise)

Authentication and authorization are separate responsibilities.

---

# 15. Session Management

Users should be able to:

- View active sessions
- Sign out from other devices
- Reset passwords securely

Sessions should expire automatically after inactivity.

---

# 16. Audit Requirements

Every permission-sensitive action must be logged.

Examples:

- Login
- Logout
- Role Assignment
- Permission Changes
- User Suspension
- Approval Actions

Logs must remain immutable.

---

# 17. Future Expansion

The permission system should support future features such as:

- Custom Roles
- Department-based Access
- Branch-level Access
- Team-based Access
- Approval Workflows
- Delegated Authority

These additions should not require redesigning the existing permission model.

---

# 18. AI Implementation Rules

When implementing access control, AI assistants must:

- Never hard-code permissions.
- Always check permissions on the server.
- Never trust client-side role information.
- Separate authentication from authorization.
- Keep permission checks reusable.
- Follow the Identity → Role → Permission → Scope model consistently.

---

# Final Principle

A secure permission system should remain flexible enough to support future growth without becoming overly complex.

Users should have exactly the access they need—no more and no less.

The platform's security depends on consistent permission enforcement across every module.
